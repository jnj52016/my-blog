### 2.1 积分账户表

```
CREATE TABLE points_account (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    balance BIGINT NOT NULL DEFAULT 0,
    frozen_balance BIGINT NOT NULL DEFAULT 0,
    version BIGINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE KEY uk_user_id (user_id)
);
```

字段说明：

|字段|作用|
|---|---|
|`user_id`|用户编号|
|`balance`|用户积分总余额|
|`frozen_balance`|已冻结的积分|
|`version`|乐观锁版本号|
|`created_at`|创建时间|
|`updated_at`|修改时间|

可用积分计算公式：

```
available_balance = balance - frozen_balance
```

### 2.2 积分流水表

```
CREATE TABLE points_ledger (
    id BIGINT PRIMARY KEY,
    transaction_id VARCHAR(64) NOT NULL,
    business_type VARCHAR(32) NOT NULL,
    business_id VARCHAR(64) NOT NULL,

    operation_type VARCHAR(32) NOT NULL,
    amount BIGINT NOT NULL,
    balance_before BIGINT NOT NULL,
    balance_after BIGINT NOT NULL,
```

```
ADJUST    调账
```

## 三、第二阶段：建立账务规则

普通 CRUD 主要回答：

> 当前的数据是多少？

账务系统还必须回答：

> 为什么是这个数？是谁在什么时候通过什么业务修改的？

### 3.1 账务规则 TODO

- 积分统一使用整数类型，例如 `BIGINT`
    
- 不使用浮点数保存积分
    
- 流水生成后不允许修改
    
- 流水生成后不允许删除
    
- 修正错误时必须增加一条调账流水
    
- 每次余额变化都必须对应流水
    
- 每一笔业务必须有唯一业务编号
    
- 流水保存操作前余额
    
- 流水保存操作后余额
    
- 所有余额修改必须经过积分服务
    

错误退款方式：

```
UPDATE points_ledger
SET operation_type = 'REFUND'
WHERE id = 100;
```

正确退款方式：

```
原消费流水：CONSUME  -30
新增退款流水：REFUND   +30
```

## 四、第三阶段：实现安全扣积分

### 4.1 错误实现

不要使用“先查询、再更新”：

```
1. 查询余额为 100
2. 在程序中判断余额是否足够
3. 将余额更新为 70
```

两个并发请求可能同时查询到余额为 100，从而造成超扣。

### 4.2 正确实现

使用数据库条件更新：

```
UPDATE points_account
SET balance = balance - :amount,
    version = version + 1,
    updated_at = NOW()
WHERE user_id = :userId
  AND balance - frozen_balance >= :amount;
```

判断受影响行数：

```
影响 1 行：扣减成功
影响 0 行：账户不存在或可用积分不足
```

### 4.3 数据库事务流程

```
开始事务

1. 检查 transaction_id 是否已经处理
2. 原子扣减积分
3. 检查受影响行数
4. 查询扣减后的余额
5. 写入积分流水
6. 提交事务
```

伪代码：

```
@Transactional
public ConsumeResult consume(ConsumeCommand command) {
    Ledger existing = ledgerRepository.findByTransactionId(
        command.transactionId()
    );

    if (existing != null) {
        return ConsumeResult.from(existing);
    }

    int affectedRows = accountRepository.consume(
        command.userId(),
        command.amount()
    );

    if (affectedRows == 0) {
        throw new InsufficientPointsException();
    }

    Account account = accountRepository.findByUserId(
        command.userId()
    );

    ledgerRepository.insert(
        command,
        account.getBalance() + command.amount(),
        account.getBalance()
    );

    return ConsumeResult.success(account.getBalance());
}
```

### 4.4 并发验收标准

初始余额为 100，同时发送 100 个请求，每个请求扣除 2 积分：

- 最多成功 50 个请求
    
- 其他请求返回余额不足
    
- 最终余额为 0
    
- 最终余额不能小于 0
    
- 成功消费流水数量为 50
    
- 流水消费总额为 100

## 五、第四阶段：实现接口幂等

网络超时后，订单服务可能重复发送消费请求。

客户端每次业务操作必须提供：

```
{
  "transactionId": "tx-20260831-00001",
  "businessType": "ORDER",
  "businessId": "order-10001",
  "userId": 100,
  "amount": 30
}
```

### 5.1 幂等处理流程

```
收到消费请求
    ↓
查询 transaction_id
    ↓
已经存在？
    ├── 是：返回第一次处理结果
    └── 否：执行积分扣减并写入流水
```

### 5.2 幂等 TODO

- `transaction_id` 添加唯一约束
    
- 订单消费操作添加业务唯一约束
    
- 重复请求返回第一次的结果
    
- 重复请求不能再次扣积分
    
- 相同幂等编号、不同请求参数必须拒绝
    
- 数据库唯一键冲突时重新查询原处理结果
    

### 5.3 验收标准

- 同一个请求发送 10 次，只产生一条流水
    
- 同一个订单只能成功消费一次
    
- 客户端超时重试不会多扣积分
    
- 已成功的请求重复调用仍返回成功
    
- 相同 `transaction_id` 使用不同金额时返回错误

## 六、第五阶段：实现冻结积分

真实业务中，下单时可以先冻结积分，订单完成后再正式消费。

状态流转：

```
AVAILABLE
    ↓
FROZEN
    ├──→ CONSUMED
    └──→ RELEASED
```

需要实现四个操作：

- `freeze`：冻结积分
    
- `commit`：确认消费
    
- `cancel`：释放冻结积分
    
- `refund`：消费完成后退款
    

### 6.1 冻结积分

```
UPDATE points_account
SET frozen_balance = frozen_balance + :amount,
    version = version + 1
WHERE user_id = :userId
  AND balance - frozen_balance >= :amount;
```

### 6.2 确认消费

```
UPDATE points_account
SET balance = balance - :amount,
    frozen_balance = frozen_balance - :amount,
    version = version + 1
WHERE user_id = :userId
  AND frozen_balance >= :amount;
```

### 6.3 释放冻结积分

```
UPDATE points_account
SET frozen_balance = frozen_balance - :amount,
    version = version + 1
WHERE user_id = :userId
  AND frozen_balance >= :amount;
```

### 6.4 验收标准

- 冻结后不能使用被冻结的积分
    
- 冻结积分不能超过可用积分
    
- 确认消费只减少一次总余额
    
- 取消订单能够释放冻结积分
    
- 重复确认不会重复扣减
    
- 重复取消不会重复释放
    
- 已确认消费的冻结记录不能再取消
    
- 已取消的冻结记录不能再确认

## 八、第七阶段：实现 Transactional Outbox

不能简单地执行：

```
1. 数据库扣减积分
2. 发送消息
```

因为可能出现：

```
积分已经扣减成功
应用在发送消息前宕机
订单服务永远不知道积分已经扣除
```

### 8.1 本地消息表

```
CREATE TABLE outbox_message (
    id BIGINT PRIMARY KEY,
    message_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(64) NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(16) NOT NULL,
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_at DATETIME NULL,
    created_at DATETIME NOT NULL,
    sent_at DATETIME NULL,
    UNIQUE KEY uk_message_id (message_id)
);
```

### 8.2 正确处理流程

```
同一个数据库事务：

1. 修改积分余额
2. 写入积分流水
3. 写入 outbox_message
4. 提交事务

后台发送任务：

5. 扫描待发送消息
6. 发送到消息队列
7. 标记消息为已发送
8. 失败时稍后重试
```

### 8.3 Outbox TODO

- 创建本地消息表
    
- 余额、流水、消息在同一事务内写入
    
- 实现消息发送任务
    
- 实现失败重试
    
- 设置最大重试次数
    
- 记录最后一次失败原因
    
- 长时间失败的消息进入告警队列
    
- 消费者根据 `message_id` 去重
    

### 8.4 验收标准

- 消息发送失败后可以自动重试
    
- 同一消息投递多次只处理一次
    
- 事务提交后应用宕机，消息最终仍能发送
    
- 数据库事务回滚时不会产生业务消息
    
- 消息乱序时业务状态不会倒退

## 九、第八阶段：实现消息消费幂等

消息队列通常只能保证消息“至少投递一次”，因此消费者必须允许重复消息。

创建消费记录表：

```
CREATE TABLE consumed_message (
    id BIGINT PRIMARY KEY,
    consumer_name VARCHAR(64) NOT NULL,
    message_id VARCHAR(64) NOT NULL,
    consumed_at DATETIME NOT NULL,
    UNIQUE KEY uk_consumer_message (
        consumer_name,
        message_id
    )
);
```

消费流程：

```
开始事务

1. 插入 consumed_message
2. 如果唯一键冲突，说明已经处理，直接返回成功
3. 执行业务逻辑
4. 提交事务
5. 确认消息
```

## 十、第九阶段：建立对账系统

账务系统不能假设自己永远不会出错，必须主动发现问题。

### 10.1 账户与流水对账

检查：

```
账户当前余额
是否等于
初始余额 + 所有积分变动流水之和
```

### 10.2 业务与账务对账

检查：

- 已使用积分的订单是否存在消费流水
    
- 消费流水是否存在对应订单
    
- 订单消费金额是否等于积分流水金额
    
- 已取消订单是否已经释放冻结积分
    
- 已退款订单是否存在退款流水
    

### 10.3 每日对账报告

```
对账日期：
账户总数：
消费订单数：
消费流水数：
消费积分总额：
余额不一致账户数：
缺少流水的订单数：
缺少订单的流水数：
待处理异常数：
```

### 10.4 异常处理原则

发现错误后：

```
1. 记录对账异常
2. 保存异常证据
3. 人工或自动确认
4. 生成调账流水
5. 再次执行对账
```

禁止直接修改历史流水。

## 十一、第十阶段：故障演练

主动模拟以下故障：

- 请求超时，但数据库事务已经提交
    
- 数据库死锁
    
- 数据库连接中断
    
- 服务处理到一半突然退出
    
- 消息发送失败
    
- 消息重复发送
    
- 消息延迟
    
- 消息乱序
    
- 消费者处理成功但消息确认失败
    
- 两个请求同时消费最后一笔积分
    
- 对账任务执行到一半失败
    
- Outbox 发送任务重复启动
    

系统必须始终满足：

```
余额永远不能为负
同一业务只能入账一次
每次余额变化都有流水
流水能够重新计算出余额
失败操作可以安全重试
系统故障后最终可以恢复一致
```
