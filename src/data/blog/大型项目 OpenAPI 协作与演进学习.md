# 大型项目 OpenAPI 协作与演进学习 TODO

## 学习目标

- 理解“项目分期”“OpenAPI 文件拆分”和“API 版本”是三件不同的事
- 能把一个很大的 OpenAPI 按业务域拆成多个容易维护的文件
- 能使用 `components` 和 `$ref` 复用资源、参数、响应和安全方案
- 能判断一次接口修改是否会破坏已经上线的客户端
- 能为一期、二期、三期设计可持续演进的接口，而不是每期推倒重来
- 能建立前端、后端、测试和产品都能执行的接口变更流程
- 能通过自动检查发现重复定义、无效引用和不兼容变更
- 最终整理出一套以后做大型项目可以直接复用的 OpenAPI 模板和协作规范

---

## 一、先建立完整认识

需要先分清下面三个概念：

```text
一期、二期、三期
    ↓
管理每次交付哪些业务能力

OpenAPI 文件拆分
    ↓
管理接口文档怎样组织、复用和协作

API v1、v2
    ↓
管理无法向后兼容的接口变化
```

二期增加功能，并不等于必须创建 API v2。只要二期的变化不会破坏一期调用方，就可以继续在原版本上新增接口或字段。

## 二、学习 Contract First

Contract First 的基本顺序：

```text
提出需求
  ↓
设计并修改 OpenAPI
  ↓
前端、后端、测试共同评审
  ↓
确定接口契约
  ↓
各方并行开发
  ↓
联调与验收
```

OpenAPI 不应该是后端写完代码以后补的一份说明书，而应该是各方开发前共同确认的契约。

## 三、把巨大的 OpenAPI 拆开

目标目录结构：

```text
openapi/
├─ root.yaml
├─ paths/
│  ├─ users.yaml
│  ├─ orders.yaml
│  └─ payments.yaml
├─ components/
│  ├─ schemas/
│  │  ├─ UserResponse.yaml
│  │  ├─ OrderResponse.yaml
│  │  └─ Money.yaml
│  ├─ parameters/
│  │  ├─ Page.yaml
│  │  └─ PageSize.yaml
│  ├─ responses/
│  │  ├─ BadRequest.yaml
│  │  └─ NotFound.yaml
│  └─ securitySchemes/
└─ dist/
   └─ openapi.bundle.yaml
```

维护原则：

- 源文件按业务域和职责拆分
- `root.yaml` 只作为总入口
- `dist/openapi.bundle.yaml` 由工具自动生成
- 团队只修改源文件，禁止直接修改合并产物
- 不要单纯按一期、二期建立两套互相复制的 OpenAPI

## 四、掌握 `components` 和 `$ref`

适合复用的内容：

- 分页、排序、租户 ID、请求追踪 ID
- 金额、日期范围、地址等稳定值对象
- 通用错误响应
- 鉴权方案
- 明确属于同一个业务概念的模型

不应该为了少写几行代码而强行复用：

- 只是碰巧字段相同的两个业务对象
- 创建请求和查询响应
- 内部管理接口和外部开放接口
- 生命周期不同、以后可能独立变化的模型

## 六、判断兼容性变更和破坏性变更

### 通常可以兼容的变化

- 新增接口
- 新增可选请求参数
- 响应中新增字段
- 新增可选能力
- 修正文档、示例和描述

注意：响应新增字段虽然通常兼容，但客户端必须能够忽略未知字段；枚举增加新值也可能让写死分支的客户端出错。

### 通常会破坏已有调用方的变化

- 删除或重命名字段
- 把可选参数改成必填
- 修改字段类型或业务含义
- 修改 URL 或 HTTP 方法
- 修改状态码语义
- 修改认证方式
- 删除枚举值
- 将数组改成对象，或改变响应整体结构

## 七、学习接口废弃和版本迁移

当二期确实需要改变一期接口时，依次考虑：

1. 能不能只增加新字段或新接口
2. 能不能让服务端暂时同时支持新旧格式
3. 能不能将旧字段或旧接口标记为废弃，并给出迁移期限
4. 如果语义和结构变化太大，再建立新版本

迁移过程：

```text
旧接口正常使用
    ↓
发布新接口或新字段
    ↓
旧接口标记 deprecated
    ↓
通知调用方并统计迁移情况
    ↓
完成客户端迁移
    ↓
经过约定期限后再删除旧接口
```

## 八、设计接口变更单

每次修改 OpenAPI 时附带一份简短变更说明：

```text

所属需求：REQ-2-015
所属阶段：二期
影响接口：GET /orders/{orderId}
变更类型：兼容新增 / 破坏性变更
变更内容：响应增加 estimatedDeliveryTime
影响对象：前端、后端、测试、外部合作方
兼容方案：旧客户端忽略新字段
迁移期限：如有废弃内容则填写
```

## 十、加入自动检查

每次提交至少自动检查：

- YAML 或 JSON 语法是否正确
- OpenAPI 结构是否合法
- `$ref` 是否能够解析
- `operationId` 是否唯一
- 命名和路径是否符合团队规范
- 是否出现未使用或重复的定义
- 与主分支相比是否存在破坏性变化
- 多文件是否能正确生成发布版本

## 十一、处理一期、二期、三期的正确方式

不要这样维护：

```text
openapi-phase-1.yaml
openapi-phase-2-copy.yaml
openapi-phase-3-final-final.yaml
```

这种做法会产生多份相似定义，不知道哪一份才是真实契约。

推荐方式：

- 主分支保存当前有效的完整接口契约
- 使用 Git 标签或发布版本保存每次正式发布的历史状态
- 二期在当前契约上进行兼容新增
- 旧能力需要废弃时走迁移流程
- 只有无法兼容的重大变化才建立新 API 版本
- 需求文档通过“本期范围”说明一期和二期各自交付什么
